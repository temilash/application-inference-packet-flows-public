Problem Statement

Modern mobile networks carry traffic from video streaming, social networking, web browsing, messaging, map services, notification processing, and many other applications over shared encrypted network paths. These applications have different bandwidth, latency, and reliability requirements, but direct application identifiers are often unavailable because payloads are encrypted and privacy-sensitive metadata is removed.

The task is to build an AI/ML method that estimates the application associated with each communication flow using only statistical packet-flow features. Participants must infer the application without relying on payload contents, IP addresses, DNS query names, TLS SNI, HTTP Host values, URLs, or domain strings.

This problem is important for application-aware network management, including QoS control, traffic prioritization, network slicing, congestion mitigation, anomaly detection, and resource-efficient real-time operation.

Objective

The objective of this challenge is to develop a model that predicts application labels for encrypted mobile traffic flows from flow-level features. Participants will design methods that use traffic volume, direction, packet size, inter-arrival time, burstiness, flow duration, and related statistics.

The challenge emphasizes practical deployment in real networks, not only classification accuracy. Important perspectives include early identification from the first few packets, robustness under class imbalance, lightweight model design, overfitting prevention, and clear handling of uncertain predictions.

Approach

Participants may freely design the feature processing and learning pipeline. Possible components include feature selection, feature transformation, normalization, dimensionality reduction, model selection, class-imbalance handling, and generalization methods for applications with few samples.

Flow-statistics approach

Use packet counts, byte counts, traffic direction, duration, packet-size distributions, and inter-arrival-time statistics.

Time-series approach

Model packet-size sequences, direction sequences, timing patterns, and early-flow behavior when available.

Hybrid approach

Combine domain-knowledge-based feature engineering with machine learning or sequence-aware models.

This challenge has two scored tasks with the same target application labels: facebook, google, instagram, mozilla, x, and youtube.

Dataset

The source data is a packet capture of approximately 44 minutes of traffic from a single user equipment. The organizers extract flow-level features from the packet trace and provide them to participants in CSV format.

Each task directory contains public training data, public validation data, private-evaluation features, and a sample submission template.

  • train_features.csv: flow-level features for training
  • train_labels.csv: ground-truth labels for training flows
  • validation_features.csv: flow-level features for validation
  • validation_labels.csv: ground-truth labels for validation flows
  • test_features.csv: flow-level features for final evaluation
  • sample_submission.csv: submission template
Dataset access: the participant-facing dataset is provided in the public repository FG-AI4H/application-inference-packet-flows-public under dataset/. Final test labels are held only by the organizers and are not included in the participant-facing files.

The feature files include information such as flow duration, transport protocol, server-side port, uplink/downlink packet counts, uplink/downlink byte counts, packet-size statistics, inter-arrival-time statistics, burst counts, and uplink/downlink ratios.

The following information is not included in the participant feature files: IP addresses, DNS query names, TLS SNI, HTTP Host values, URLs, domain strings, or payload contents.

Conditions

  • Ground-truth labels for final evaluation data must not be used for training or model selection.
  • Full-flow features from Task 1 must not be used to generate Task 2 predictions.
  • Participants must not attempt to recover direct identifiers such as DNS names, TLS SNI, HTTP Host values, IP addresses, URLs, domain strings, or payload contents.
  • If information other than the provided feature files is used, it must be clearly described in the submitted technical report.
  • The organizers may inspect submitted code, reports, and prediction files to confirm compliance with these rules.
